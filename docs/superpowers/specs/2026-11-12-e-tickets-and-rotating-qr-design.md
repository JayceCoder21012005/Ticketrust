# E-tickets & Rotating QR — Design (spec 10)

Source of truth for behaviour: `specs/10-e-tickets-and-rotating-qr.md`. This document only fixes **scope and build decisions**. Written by the controller while the user was away: every open point is a *ruling* (listed at the end), not a question.

## Intent

Buyers see their tickets in a wallet and each ticket shows a QR that changes every 15 s, so a screenshot is worthless. The client computes the code itself (Web Crypto) from a per-ticket secret, so it keeps rotating offline at the venue. The gate (spec 11) verifies with `QrCodeService`, accepting step ±1.

## What already exists (do not rebuild)

- `Ticket` aggregate (spec 08): `QrSecret` 32 random bytes, encrypted at rest through a Data Protection value converter (`TicketSecretProtection.cs`), statuses `Valid | CheckedIn | Listed | Voided`, `OwnerUserId`, `EventId`, `TierId`, `SeatIndex` (null = general admission).
- Orders API/views with seat labels (`Application/Features/Orders/OrderViews.cs` `LoadSeatLabelsAsync`, section/row/number from `EventSeat`) and the web order pages (`web/src/features/orders`, `/account/orders/[orderId]`); spec 09's "Xem vé" email link points at `/account/orders/{orderId}`.
- `shared/fixtures/seat-layout.json` is the existing pattern for fixtures shared by C# and TypeScript tests.
- Web: Next 16, Vitest + jsdom, Playwright against a production build with a mock API (`web/e2e`, `context.route` scripting), `sonner`, TanStack Query, lazy islands, a 170 KB public-bundle budget.

## QR format (pinned — the spec text is ambiguous in three places)

```
TR1.<ticketId b64url>.<step>.<sig b64url>
ticketId b64url = base64url (no padding) of the 16 RFC 4122 bytes of the Guid in network order (Guid.ToByteArray(bigEndian: true)) -> 22 chars
step            = floor(unixSeconds / 15), decimal, no padding
sig             = base64url(HMAC-SHA256(secret, UTF8(ticketIdCanonical + "|" + step))[0..10]) -> 14 chars
ticketIdCanonical = lowercase hyphenated "D" format, e.g. 0192f0e0-aaaa-7bbb-8ccc-0123456789ab
```
Payload ≈ 50 chars. `step` has no leading zeros. Verification compares signatures in constant time and accepts `|step − currentStep| ≤ 1`.

## Backend

- `IQrCodeService` (Application/Abstractions/Tickets) + `QrCodeService` (Infrastructure/Tickets; spec names Infrastructure as owner): `string Encode(Guid ticketId, ReadOnlySpan<byte> secret, long unixSeconds)`, `bool TryParse(string code, out ParsedQrCode parsed)` (`ParsedQrCode(Guid TicketId, long Step, byte[] Signature)`; rejects wrong prefix/shape/oversize), `bool Verify(ParsedQrCode parsed, ReadOnlySpan<byte> secret, long unixSeconds)`. Pure, no I/O. Spec 11 will call `TryParse`, load the secret by ticket id, then `Verify`.
- Shared vectors: `shared/fixtures/qr-vectors.json` — 1 000 random cases (secret base64, ticketId, unixSeconds, expected code) generated by a **C# generator test with a fixed seed** and committed; the C# test re-verifies every vector, the TypeScript test regenerates every code and must match exactly.
- API (all `RequireAuthorization`, owner only, 404 `ticket.not_found` for unknown or foreign ids — one code, no oracle): `GET /api/v1/me/tickets?scope=upcoming|past` (grouped by event: id, slug, title, cover, startsAt, endsAt, venue name + city, status, `tickets[]`: id, orderId, tier name, `seat {section,row,number}|null`, status, holderName; keyset not required: a user has few tickets, but the response is capped at 200 tickets and sorted by event start (upcoming asc, past desc)); `GET /api/v1/tickets/{id}` (detail incl. event summary, tier, seat labels, holder name, status, and `orderTicketIds[]` for sibling navigation); `GET /api/v1/tickets/{id}/qr-key` → `{ ticketId, secret (base64), stepSeconds: 15, format: "TR1" }` only when `Valid` and the event has not ended and is not cancelled, else 409 `ticket.not_displayable`; `Cache-Control: no-store` on all three; `qr-key` limited to 10 requests/min per user (429, ProblemDetails with `Retry-After`).
- Rate limit: a small Redis fixed-window limiter behind `IQrKeyThrottle` (Application) using ONE Lua script in `Infrastructure/Redis/Scripts` (INCR + EXPIRE, keys under the usual `tr:{env}:` prefix); fail CLOSED (503 `system.busy`) if Redis is down, consistent with spec 00. Spec 12 replaces it with its named sliding-window policy `qr-key`.
- Scope: `upcoming` = event not ended (`EndsAt > now`) and not cancelled and ticket not Voided; `past` = everything else the user owns. Cancelled event → `past` (tickets Voided).
- Holder name = the owner's `FullName`. `CheckedIn` carries no time yet (spec 11 owns check-in): the DTO has no `checkedInAt`; the overlay says "Đã check-in" without a time until 11 adds it.

## Frontend

- Pure TS `lib/tickets/qr-code.ts`: `qrPayload(ticketId, secretBytes, unixSeconds): Promise<string>` using `crypto.subtle` (HMAC-SHA256), matching the C# format and the shared vectors; plus `currentStep`, `msUntilNextStep`.
- QR rendering: an **in-repo** byte-mode QR encoder (`lib/tickets/qr-matrix.ts`, versions 1–10, ECC level M, mask selection per ISO 18004) — no new dependency (adding one would force a `web/package-lock.json` change, which the user forbids staging). Dynamically imported by the wallet screen only. Verified against a real decoder in a throwaway Python venv (zxing-cpp or opencv, NEVER committed): render matrices for sample payloads and decode them; commit a few reference matrices as test vectors.
- `/account/tickets` tabs *Sắp diễn ra* / *Đã qua*, cards (cover, date, venue, ticket count), empty state linking to the catalog; `/tickets/[id]` wallet screen (QR regenerated each 15 s with a circular progress ring, animated gradient band + live clock under the QR, seat info large (Khu / Hàng / Ghế), tier, holder, event date + venue, "Thêm vào lịch" (client-side `.ics`), brightness tip, status overlays: *Đã check-in*, *Đang rao bán* (QR hidden), *Đã huỷ*; swipe/arrow navigation between sibling tickets of the order; `prefers-reduced-motion` stops the gradient but keeps the clock).
- Offline: `qr-key` responses stored in IndexedDB per ticket (deleted after the event ends), a small service worker caching the wallet route shell + its assets so `/tickets/[id]` opens without signal; the rotating QR keeps working from the cached key. The cached secret is a credential: it is removed on logout and never written anywhere else.
- The order detail page (spec 08) links to the ticket wallet once the order is paid; the spec 09 email "Xem vé" link is left on `/account/orders/{id}` (the order page leads to the tickets).

## Constraints

- Spec 00 coding rules and API conventions (ProblemDetails with `code`, ownership 404, OpenAPI regenerated + typed client). Vietnamese copy, axe clean in light and dark, keyboard accessible, loading/empty/error states, 170 KB public-bundle budget untouched (the wallet/QR code only loads on buyer routes).
- `web/package-lock.json` is never staged; no new web dependency.
- No PII/secrets in logs; the secret appears only in the `qr-key` response body.
